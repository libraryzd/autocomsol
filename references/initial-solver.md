# Initial solve with the default solver and a 200 iteration cap

For a new task's initial model bring-up, start with the solver sequence automatically generated from the actual study/physics. Prefer this over constructing or copying a customized solver tree before observing a failure. Preserve a supplied model's user-defined settings unless the approved task calls for changing them; record that exception. The value **200** is the user's preferred starting maximum, not COMSOL's default or a guarantee of convergence.

## Apply before the first solve

1. After the task-specific physics/study setup, generate/show the default solver sequence without solving. COMSOL 6.3 documents `model.study(studyTag).createAutoSequences('all')` and `showAutoSequences('sol')` as ways to generate the sequence. Use the installed version's supported method on the owned task model. See the [official Study guide](https://doc.comsol.com/6.3/doc/com.comsol.help.comsol/application_programming_guide.15.27.html).
2. Inspect the generated sequence, actual feature types/tags, active study steps and termination controls. Do not assume `sol1/s1/fc1` or select the first solver in an unrelated user's model. Keep the generated coupling approach, linear solver/preconditioner, default tolerances/scaling and convergence tests unless evidence requires a targeted change.
3. Set the applicable **main nonlinear/segregated maximum iteration cap to 200**. For 6.3, a FullyCoupled feature exposes `maxiter`; a Segregated feature exposes `maxsegiter`, which is active with `segterm='tol'`. Other termination modes use different controls; do not replace convergence-based stopping with a fixed iteration count to force a nominal value of 200. Verify the effective setting for the actual mode before proceeding. Sources: [FullyCoupled API](https://doc.comsol.com/6.3/doc/com.comsol.help.comsol/comsol_api_solver.51.28.html), [Segregated API](https://doc.comsol.com/6.3/doc/com.comsol.help.comsol/comsol_api_solver.51.41.html).
4. Read back the set value and record the node path/type, property, original value, effective value and active termination mode in `logs/solver-settings.json` or equivalent task metadata. Run the owned sequence without subsequently regenerating it and losing the setting. If regeneration is required, re-inspect and reapply applicable settings before the next solve.

Do not blindly set every nested `maxiter` property. Linear iterative solver limits, nonlinear iterations, segregated substeps, time-step counts, eigenvalue iterations and outer optimization loops are different controls. A purely linear/direct setup may not have an applicable nonlinear cap; record “not applicable” rather than creating an unnecessary nonlinear loop. If the applicable property is unavailable or a termination mode makes the intended cap ineffective, inspect version-matched documentation and report the concrete limitation, rather than falsely reporting that the limit was applied.

For time-dependent studies, a nonlinear iteration limit may apply within individual time steps; it is not a limit of 200 total time steps. Reaching the maximum without convergence remains a failure. Keep task accuracy and physics unchanged while diagnosing it. Only then make justified solver changes within the approved scope and compute budget; log what changed and why, and update the final Word plan to reflect the actual adopted settings. The 200 preference does not replace the separate three-level relative-tolerance validation selected after baseline success.

The bundled historical benchmark's solver function is unchanged and does not implement/read back this 200 cap. Use this procedure in newly generated task drivers; do not claim an old regression run verified it. The cited API behavior was checked against COMSOL 6.3 documentation on 2026-09-30; other versions require matching documentation/live inspection.
